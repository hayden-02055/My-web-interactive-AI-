## 0. 통합 근거 및 MVP 범위 조정

### 0.1 세 SDD를 묶는 이유

SDD-05·06·07은 모두 **SDD-04 상태 모델의 표현 계층**이다. 새로운 데이터 흐름을 만들지 않고, 이미 수집된 `suggestions` · `trace` · `blocks`를 렌더링한다.

```text
[SDD-04] AssistantMessage
    ├── suggestions[]  → SDD-05  제안 카드
    ├── trace[]        → SDD-06  X-ray
    └── blocks[]       → SDD-07  MVP outline
```

세 영역이 같은 메시지 컴포넌트 안에 함께 배치되므로, 레이아웃·시각 언어·상호작용 규칙을 분리해 정의하면 오히려 충돌한다. 하나의 문서로 통합한다.

### 0.2 MVP 범위 조정

**구 SDD-08 (Contact & CTA) 폐기**

PRD §15의 P0 항목 `Contact CTA`는 다음으로 이미 충족된다.

| 경로 | 담당 |
|---|---|
| Agent 제안 CTA | SDD-03 `suggest_contact` + 본 문서 §1 |
| 정적 Contact (FR-12) | SDD-01 |

구 SDD-08에 남는 폼 백엔드·메일 전송·스팸 방어는 P0에 없다. MVP에서 제외한다.

**구 SDD-09 → SDD-08 (MVP Closure)로 재정의**

`Persistent Agent`는 P0이나 SDD-01은 모바일에서 패널을 렌더링하지 않는다. 모바일 셸이 없으면 P0가 미충족 상태로 남는다. 따라서 다음만 남긴 슬림 문서로 재정의한다.

- 모바일 Agent 셸 (PRD §14 Responsive)
- INV-01 최종 격리 검증
- 기본 키보드 접근성

### 0.3 본 문서에서 다루지 않는 것

| 항목 | 상태 |
|---|---|
| Case Study 필터링 | P1 |
| 대화 → Contact 요약 | P1 |
| Analytics | P1 |
| 모바일 셸 · 접근성 전반 | SDD-08 (재정의) |

## 1. SDD-05 — Navigation Suggestion

> **Covers**: FR-05, FR-06, FR-11

### 1.1 목표

Agent가 제안한 콘텐츠 위치와 Contact CTA를 클릭 가능한 카드로 표현하고, **사용자 클릭 이후에만** 이동을 실행한다.

### 1.2 Design Decisions

#### DD-26 · 제안 클릭은 완전한 클라이언트 경로다

카드 클릭 시 어떤 네트워크 요청도 발생하지 않는다. `suggestion` 이벤트의 `target`을 DOM 앵커로 해석하여 스크롤한다.

**근거**

> INV-02 — 결정론적 경로는 네트워크를 타지 않는다.
> PRD §11 — `suggest_section()`은 `{label, target}`만 반환하고 실제 Navigation은 클라이언트가 처리한다.

이 경로가 이 제품의 체감 인터랙티브 대부분을 담당한다. 서버 왕복이 끼어드는 순간 "Agent가 붙은 느린 사이트"가 된다.

#### DD-27 · 앵커 부재 시 조용히 실패하지 않는다

`target` 앵커가 DOM에 없으면 카드를 **비활성 상태로 표시**하고 이동을 시도하지 않는다.

**근거**

SDD-03 §4.3이 서버에서 앵커 존재를 검증하므로 정상적으로는 발생하지 않는다. 그러나 콘텐츠 변경과 인덱스 갱신 사이의 시차, 혹은 조건부 렌더링으로 앵커가 일시 부재할 수 있다.

이때 클릭해도 아무 일이 없는 것이 **가장 나쁜 결과**다. 사용자는 사이트가 고장 났다고 판단한다. 비활성 표시는 정직하고, 개발 중에는 콘솔 경고로 조기 발견을 돕는다.

#### DD-28 · 이동 후 대상 섹션을 짧게 강조한다

스크롤 완료 후 대상 요소에 일시적 강조를 적용하고, 포커스를 이동시킨다.

**근거**

- 긴 문서에서 스크롤만으로는 "어디로 왔는지"가 불분명하다
- 포커스 이동은 키보드·스크린리더 사용자에게 필수다. 시각적 스크롤만으로는 접근성 경로가 끊긴다
- `prefers-reduced-motion` 존중 — 해당 설정 시 부드러운 스크롤 대신 즉시 이동

### 1.3 Suggestion 카드 유형

SDD-03 §5.7의 `type`에 따라 분기한다.

| type | 표시 | 동작 |
|---|---|---|
| `section` | 라벨 + 이동 아이콘 | 앵커 스크롤 (DD-26) |
| `contact` | 강조된 CTA | Contact 섹션으로 스크롤 |

`reason`은 카드 보조 문구로 표시한다. 제안 이유를 밝히는 것이 PRD §9.3의 "Agent suggests. User decides." 를 강화한다.

**Contact CTA (FR-11)**

`type: contact`는 시각적으로 구분되는 primary 스타일을 사용한다. PRD §17의 핵심 퍼널 `Agent → Case Study → Contact`의 종착점이다.

### 1.4 배치

제안 카드는 답변 텍스트 **아래**, 메시지 하단에 배치한다.

**근거**

답변을 읽기 전에 버튼이 먼저 보이면 사용자가 콘텐츠를 건너뛰고 클릭하게 된다. PRD §16의 비목표 "사용자의 모든 행동을 Agent가 제어하는 UI"에 가까워진다.

### 1.5 시작 프롬프트 (O-18 결정)

대화가 비어 있을 때 3~4개의 시작 질문을 제시한다. **전송 전까지는 입력창을 채우기만 하고 자동 전송하지 않는다.**

**근거**

PRD §15에서 `Agent suggested questions`는 P1이나, 빈 입력창은 방문자의 첫 상호작용 장벽이 크다. PRD §17의 `Agent interaction rate` 개선 효과 대비 구현 비용이 매우 낮다.

자동 전송하지 않는 이유는 INV-04와 같은 원칙이다 — 사용자가 결정한다.

질문은 정적 상수로 관리한다. 생성하지 않는다.

## 2. SDD-06 — Chat Process X-ray

> **Covers**: FR-09, FR-10

### 2.1 목표

Agent 실행 과정을 2단계로 공개한다. 기본은 파이프라인, 확장하면 실행 상세.

**부수 효과가 본질에 가깝다** — 답변 대기 시간이 "빈 로딩"이 아니라 "관찰 가능한 진행"이 된다. 이것이 SDD-00 단계에서 지연 대응책으로 채택된 이유다.

### 2.2 Design Decisions

#### DD-29 · 5개 슬롯은 클라이언트가 미리 그리고, 서버 이벤트로 채운다

SDD-03 DD-12의 대응 결정이다. 서버는 실제 발생한 이벤트만 발행하고, 클라이언트가 PRD §10.1의 5단계 슬롯을 선배치한다.

```text
Understanding          ← 이벤트 수신 전에도 슬롯 존재
Finding Context
Retrieving Experience
Selecting Action
Generating Answer
```

**슬롯 상태 표현**

| 상태 | 근거 이벤트 | 표시 |
|---|---|---|
| 대기 | 없음 | 흐리게 |
| 진행 중 | `status: started` | 활성 + 진행 표시 |
| 완료 | `status: completed` | 완료 + 소요시간 |
| 건너뜀 | `status: skipped` | 흐리게 + 사유 |
| 실패 | `status: failed` | 오류 표시 |

**근거**

PRD §10.1의 UX(고정 파이프라인)와 INV-05(실제 실행 반영)가 충돌하지 않는 유일한 배치다. 슬롯은 UI 구조이고, 채움은 실행 사실이다.

#### DD-30 · 스키마에 정의된 필드만 렌더링한다

`detail` 객체를 순회하여 자동 렌더링하지 않는다. stage별로 알려진 필드만 명시적으로 표시한다.

**근거**

> INV-05 — system prompt · hidden reasoning · secret · 민감한 모델 입력을 공개하지 않는다.

SDD-03 §5.9가 서버측 유출을 차단한다. 클라이언트에서 미지 필드를 자동 렌더링하면 그 방어가 무의미해진다. **양쪽 모두 허용 목록 방식**이어야 한다.

미지 필드는 무시하되 개발 모드에서 경고를 남긴다.

#### DD-31 · 스트리밍 중 펼침, 완료 후 접힘

| 시점 | 상태 |
|---|---|
| 스트리밍 중 | 파이프라인 펼침 — 진행 관찰 |
| `answer.done` | 한 줄 요약으로 접힘 |
| 사용자 클릭 | Technical Detail 펼침 |

접힌 요약은 단계 수와 총 지연을 표시한다.

**근거**

- 대기 중에는 파이프라인이 보여야 지연이 관찰로 전환된다
- 답변이 끝난 뒤에도 5단계가 계속 펼쳐져 있으면 대화 스크롤이 파이프라인으로 뒤덮인다
- 사용자가 명시적으로 펼친 경우 그 상태를 유지한다

첫 방문 시 한 번은 자동으로 펼쳐진 채로 두어, X-ray의 존재를 발견하게 한다. 이후 메시지부터 접힘 규칙을 적용한다.

### 2.3 Technical Detail 표시 (FR-10)

SDD-03 §5.4의 stage별 `detail`을 대응 표시한다.

| stage | 표시 항목 |
|---|---|
| understanding | 메시지 길이, 히스토리 턴 수 |
| finding_context | 인식된 섹션 · Case Study |
| retrieving_experience | 검색 결과 앵커 · 라벨 · 점수, 임계값 |
| selecting_action | 실행된 tool 이름 · 상태 · 소요, 라운드 |
| generating_answer | 모델, 출력 토큰 |
| (메타) | intent, 총 지연 |

PRD §10.2의 예시 구성과 일치한다.

**검색 결과 0건의 표시**

`result_count: 0`이면 "검색을 수행했고 임계값을 넘는 결과가 없었다"를 명시한다. 빈 칸으로 두지 않는다.

**근거**

SDD-02 DD-10의 설계 의도가 여기서 사용자에게 보인다. "모른다"고 답한 근거가 X-ray에서 확인되면, 그 답변이 회피가 아니라 정직임이 드러난다. PRD §5.5를 직접 구현하는 지점이다.

**검색 결과 항목의 클릭**

검색 결과 앵커는 해당 위치로 이동 가능하게 한다. DD-26·27과 동일한 규칙을 따른다.

### 2.4 P0 / P1 경계

PRD §15에서 `Agent X-ray Basic Pipeline`은 P0, `Technical X-ray Detail`은 P1이다.

그러나 SDD-03이 이미 `detail`을 발행하므로 **추가 백엔드 작업이 0**이고, 프론트 작업만 남는다. 본 문서는 양쪽을 모두 구현 대상으로 삼되, 일정 압박 시 Technical Detail을 후순위로 내릴 수 있도록 컴포넌트를 분리한다.

## 3. SDD-07 — Solution Consulting

> **Covers**: FR-07, FR-08

### 3.1 목표

`answer.block(mvp_outline)`을 구조화된 상담 결과로 표현하고, 관련 Case Study 및 Contact로 연결한다.

### 3.2 Design Decisions

#### DD-32 · MVP outline은 산문이 아니라 구조로 렌더링한다

SDD-03 §4.4는 모델이 구조화된 인자를 전달하고 서버가 검증해 블록으로 발행하도록 설계되어 있다. 클라이언트는 이를 **전용 컴포넌트**로 렌더링한다. Markdown 텍스트로 풀지 않는다.

**근거**

- PRD §9.4의 응답 예시는 Goal · Pipeline · MVP Scope · Relevant Experience · CTA로 구성된 **구조화된 산출물**이다
- 구조를 유지하면 각 부분이 개별 상호작용 대상이 된다. Case Study는 링크가 되고, CTA는 버튼이 된다
- 모델이 매번 다른 형식으로 서술하는 것을 막아 일관성을 확보한다

#### DD-33 · Case Study 연결은 SDD-05 카드를 재사용한다

`relevant_case_studies`의 각 ID를 SDD-05의 `section` 제안 카드와 동일한 컴포넌트로 렌더링한다.

**근거**

동일한 동작(앵커 이동)에 두 가지 시각 언어를 두면 사용자가 학습을 두 번 해야 한다. DD-26·27·28의 규칙도 자동으로 상속된다.

ID → 앵커 변환은 SDD-01 §3.5 규칙(`experience-<id>`)을 따른다.

### 3.3 블록 구성

| 구성 | 출처 | 표시 |
|---|---|---|
| Goal | `goal` | 상단 요약 |
| Pipeline | `pipeline[]` | 단계 흐름 |
| MVP Scope | `mvp_scope[]` | 항목 목록 |
| Relevant Experience | `relevant_case_studies[]` | 제안 카드 (DD-33) |
| Caveats | `caveats[]` | 보조 문구 |

**Caveats 표시는 생략할 수 없다**

> PRD §9.4 — 정확한 견적이나 계약 조건은 Agent가 확정하지 않는다.

`caveats`가 비어 있어도 범위 한계에 대한 기본 문구를 표시한다. 방문자가 이 산출물을 확정된 제안으로 오해하면 실제 상담에서 문제가 된다.

### 3.4 Contact 연결

MVP outline 블록 뒤에 `suggest_contact` 제안이 발행되면 자연스럽게 이어진다. 블록 자체가 CTA를 내장하지 않는다.

**근거**

CTA 발행 여부는 서버 판단(모델의 tool 선택)이다. 블록이 항상 CTA를 포함하면 실행과 표시가 어긋난다. INV-05의 연장이다.

## 4. Cross-cutting

### 4.1 메시지 내 배치 순서

```text
┌ AssistantMessage ─────────────────┐
│  X-ray 파이프라인      (SDD-06)   │
│  답변 텍스트                       │
│  MVP outline 블록      (SDD-07)   │
│  제안 카드             (SDD-05)   │
└───────────────────────────────────┘
```

X-ray가 위, 제안이 아래다. 실행 과정 → 결과 → 다음 행동의 순서다.

#### DD-34 · 목 픽스처 기반 개발

세 영역 모두 SDD-04의 목 SSE 픽스처로 개발·검증한다. 백엔드 기동을 전제하지 않는다.

**필요 픽스처**

| # | 시나리오 |
|---|---|
| F-01 | 검색 성공 + section 제안 |
| F-02 | 검색 0건 |
| F-03 | MVP outline + Case Study 2건 + contact 제안 |
| F-04 | tool 미사용 (인사말) |
| F-05 | 스트리밍 중 실패 |
| F-06 | 존재하지 않는 앵커 제안 (DD-27 검증) |

**근거**

SDD-05·06·07은 렌더링 계층이므로 백엔드 의존이 본질적으로 없다. 픽스처 기반 개발은 재현 가능한 회귀 테스트를 남기고, 엣지 케이스(F-02·F-05·F-06)를 실제 백엔드로 재현하는 어려움을 제거한다.

### 4.2 INV-04 준수 확인

세 영역 어디에서도 **자동 이동이 발생하지 않는다.**

| 대상 | 확인 |
|---|---|
| 제안 카드 | 클릭 이벤트에서만 스크롤 |
| X-ray 검색 결과 | 클릭 이벤트에서만 스크롤 |
| MVP outline Case Study | 클릭 이벤트에서만 스크롤 |
| 시작 프롬프트 | 입력창 채움만, 전송 안 함 |

### 4.3 시각 일관성

- SDD-01 §7의 `@theme` 토큰만 사용한다. 임의 색상값을 도입하지 않는다
- 제안 카드는 유형과 무관하게 동일한 형태를 공유하고 강조만 달리한다
- X-ray는 대화 흐름을 방해하지 않도록 답변 텍스트보다 낮은 시각 무게를 갖는다

## 6. Definition of Done

### 6.1 Navigation Suggestion

- [ ] `section` 제안 클릭 → 해당 앵커로 이동
- [ ] **클릭 시 네트워크 요청 0회** (INV-02 · DevTools 확인)
- [ ] 이동 후 대상 강조 및 포커스 이동
- [ ] `prefers-reduced-motion` 설정 시 즉시 이동
- [ ] 존재하지 않는 앵커 → 카드 비활성, 클릭 무반응 아님 (F-06)
- [ ] `contact` 제안이 시각적으로 구분되고 Contact 섹션으로 이동 (FR-11)
- [ ] 시작 프롬프트 클릭 시 **입력창만 채워지고 전송되지 않음**

### 6.2 X-ray

- [ ] 스트리밍 중 5개 슬롯이 순차적으로 채워짐
- [ ] 발생하지 않은 단계가 완료로 표시되지 않음 (F-04)
- [ ] `skipped` · `failed` 상태가 구분되어 표시
- [ ] 완료 후 한 줄 요약으로 접힘, 총 지연 표시
- [ ] Technical Detail 확장 시 §2.3 항목 표시 (FR-10)
- [ ] **검색 0건이 "결과 없음"으로 명시 표시** (F-02)
- [ ] 검색 결과 앵커 클릭 시 이동
- [ ] `detail`에 미지 필드를 주입해도 렌더링되지 않음 (DD-30)
- [ ] **SSE 원문과 화면 표시를 대조해 실행과 표시가 일치** (INV-05)

### 6.3 Solution Consulting

- [ ] MVP 상담 질문 → 구조화 블록 렌더 (F-03)
- [ ] Pipeline · MVP Scope가 목록으로 표시
- [ ] `relevant_case_studies`가 이동 가능한 카드로 표시 (FR-08)
- [ ] `caveats` 비어 있어도 기본 한계 문구 표시
- [ ] 블록이 CTA를 자체 내장하지 않음 (DD-34 확인)

### 6.4 통합 · 회귀

- [ ] §4.1 배치 순서대로 렌더
- [ ] 목 픽스처 6종 전부 정상 렌더
- [ ] 실제 백엔드 연동 스모크 테스트 통과
- [ ] 임의 색상값 미사용 (토큰만 사용)
- [ ] **백엔드 중단 상태에서 포트폴리오 정상 동작** (INV-01)
- [ ] `lint` · `typecheck` · `build` 통과, 콘솔 오류 없음
